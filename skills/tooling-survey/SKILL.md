A default, not kernel — edit freely. When an exercise reaches its survey step, or the owner asks what exists for a problem:

## Using the list

1. Open `awesome-tooling.md` and find the category (or categories) the problem touches. Present the 2–3 closest entries as survey candidates — with what each does and its license — alongside anything a wider web search adds.
2. **Never present the list as the universe.** It's a verified starting map; recent tools land in the world faster than in any list. Say which candidates came from the list and which from fresh search.
3. Frame the survey per the kernel: the goal is *articulated divergence* — help the owner say which approach fits them and why, not pick a winner.

## Maintaining the list

The list stays trustworthy only if use maintains it:

- **On every use:** if a consulted entry's link is dead, its project archived, or its description no longer accurate — fix it in `awesome-tooling.md` in the same session, and note the fix in the exercise log.
- **On discovery:** a fresh-search tool that would have belonged in the list gets added (same entry format: `- [Name](canonical-repo) — factual one-liner. (LICENSE)` — verify the repo, license, and activity before writing; never add unverified).
- **Staleness sweep:** if the list hasn't been touched in ~3 months, offer the owner a refresh pass over one category (liveness check + new-candidate search) as a light exercise.
